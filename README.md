# LA VIVION — витрина помолвочных колец

Страница каталога помолвочных колец, свёрстанная по макету Figma
`1.1_Showcase/Engagemant_Rings` (десктоп, 1440). Проект собран на Nuxt 4 с
архитектурой Feature-Sliced Design, строгой типизацией и стилями на SCSS
по токенам макета.

- **Стек:** Nuxt 4, Vue 3, TypeScript (strict), SCSS + БЭМ, Pinia, vue-i18n, GSAP
- **Архитектура:** Feature-Sliced Design
- **Вёрстка:** десктоп 1440 попиксельно, планшет и мобильный по нашему решению
- **Основа:** собственный стартовый шаблон `nuxt-starter`

Проект вырос из моего стартового шаблона `nuxt-starter`: оттуда взяты
настройка сборки, линтеров и хуков, слой запросов, уведомления, i18n и
инфраструктура стилей. Под этот макет структура и токены переписаны, а
демонстрационные страницы и неиспользуемые компоненты удалены. Первый коммит в
истории — `chore: initialize project from nuxt-starter`, дальше видно, что
менялось.

## Запуск

```bash
npm install
npm run dev
```

Приложение поднимется на `http://localhost:3000`.

### Проверять работу нужно на сборке

Dev-сервер годится только для разработки. В нём страница отдаётся без сжатия,
стили подключаются отдельными файлами, картинки преобразуются при первом
обращении, а поверх работает горячая перезагрузка. Приёмка, замеры скорости и
проверка анимации по этим цифрам смысла не имеют.

```bash
npm run build
npm run preview
```

Сборка сама прогоняет линтеры и типы, а `preview` поднимает готовое приложение
на `http://localhost:3000`. Отдельно те же проверки:

```bash
npm run lint:check
npm run typecheck
npm run format:check
```

Замер скорости по собранному приложению:

```bash
npx lighthouse http://localhost:3000 --only-categories=performance --view
```

Первый заход на страницу после сборки медленнее: сервер в этот момент готовит
варианты изображений, дальше они берутся из кеша. Мерить стоит со второго
захода и на машине, не занятой другой работой.

### Публикация на GitHub Pages

Сайт выкладывается статикой в отдельный репозиторий `imrd-works.github.io`,
поэтому живёт в корне домена и базовый путь не нужен. Сборку и публикацию
делает workflow `.github/workflows/pages.yml` при пуше в `master`, его же можно
запустить вручную.

Локально то же самое:

```bash
npm run generate
npx serve .output/public
```

Что нужно настроить один раз:

1. Создать публичный репозиторий `imrd-works/imrd-works.github.io`.
2. Выпустить токен с правом записи в него и положить в секреты этого
   репозитория под именем `PAGES_DEPLOY_TOKEN`.
3. В настройках репозитория с сайтом включить Pages: источник — ветка `main`,
   папка `/`.

Файл `public/.nojekyll` обязателен: без него GitHub Pages не отдаёт папки,
начинающиеся с подчёркивания, а туда собраны и скрипты, и картинки.

> Публикация делает файлы шрифта общедоступными. Лицензия Swiss Typefaces
> этого не предполагает, решение принято владельцем проекта осознанно.

### Шрифт

В макете используется **Suisse Intl** (Swiss Typefaces). Файлы `woff2` лежат в
`public/fonts/suisse-intl/`, подключение описано в
`src/app/styles/base/_fonts.scss`. Дополнительных действий при установке не
требуется.

> **Репозиторий должен оставаться приватным.** Лицензия Swiss Typefaces
> (Basic, оформлена на LA VIVION) разрешает встраивать шрифт в сайт через
> `@font-face` только поставляемыми файлами `woff2` и требует защищать их от
> доступа третьих лиц. Публичный репозиторий это условие нарушает. Сторонние
> сервисы хостинга шрифтов лицензией тоже запрещены.

### Переменные окружения

Скопируйте `.env.example` в `.env`. Обе переменные опциональны для локальной
разработки, но `NUXT_PUBLIC_SITE_URL` нужен для корректных ссылок в Open Graph
и в карте сайта.

## Архитектура

### Слои

Код приложения лежит в `src/` и разложен по слоям Feature-Sliced Design.
Папки, которые требует Nuxt (`pages/`, `layouts/`, `plugins/`, `public/`,
`app.vue`), остались в корне: это точки входа фреймворка, а не бизнес-код.

```
src/
├── app/          инициализация: i18n, глобальные стили
├── pages/        страницы как модули
├── widgets/      самостоятельные блоки страницы
├── features/     пользовательские сценарии
├── entities/     предметные сущности
└── shared/       переиспользуемое без привязки к домену
```

Импорты идут только вниз: страница может взять виджет, виджет — фичу или
сущность, любой слой — `shared`. Обратные импорты запрещены. Из-за этого
HTTP-клиент живёт в `shared/api`, а не в `app`: к нему обращаются страницы,
а слой `app` для них недоступен.

Направление проверяет линтер, а не дисциплина: правило `import/no-restricted-paths`
описывает зоны по слоям, а `no-restricted-imports` запрещает обращаться к
внутренностям чужого слайса мимо его `index.ts`. Нарушение падает на линте и в
CI. Слой `shared` из этого запрета исключён: там нет слайсов, только сегменты.

> Слой `shared/api` — заготовка под интеграцию, а не работающая часть этой
> страницы: контент приходит из локальных моков. Транспорт, перехватчики и
> генерация типов из OpenAPI оставлены из стартового шаблона намеренно, чтобы
> подключение настоящего бэкенда не начиналось с нуля. Axios при этом
> подгружается только при первом запросе и не попадает в стартовый бандл.

### Слайсы и сегменты

Внутри слоя код разбит на слайсы по предметной области (`product`,
`page-header`, `toggle-favorite`). Внутри слайса — стандартные сегменты
методологии:

| сегмент   | что внутри                             |
| --------- | -------------------------------------- |
| `ui/`     | компоненты                             |
| `model/`  | типы, хранилища                        |
| `lib/`    | вспомогательные функции и composables  |
| `api/`    | обращения к данным                     |
| `config/` | константы, маршруты, словари переводов |

У каждого слайса есть публичный API — файл `index.ts`. Снаружи обращаются
только к нему, внутренние пути закрыты:

```ts
import { ProductCard } from "@/entities/product"; // так
import ProductCard from "@/entities/product/ui/ProductCard.vue"; // так не надо
```

Алиас в проекте один: `@` указывает на `src`. Он объявлен в `nuxt.config.ts` и
продублирован в `tsconfig.json`, потому что корневой `tsconfig` перекрывает
карту путей из `.nuxt` целиком.

### Карта страницы

```
layouts/default.vue
├── widgets/page-header          шапка: логотип, меню, иконки, кнопка
├── pages/engagement-rings       содержимое страницы
│   ├── widgets/showcase-hero        баннер с заголовком
│   ├── widgets/catalog-filters      плитки быстрых фильтров и панель фильтров
│   ├── widgets/product-shelf   ×5   заголовок категории и сетка карточек
│   ├── widgets/size-guide-banner    баннер «Не знаете размер?»
│   ├── widgets/budget-collections   подборки по бюджету
│   ├── widgets/expert-consultation  запись на просмотр
│   └── widgets/blog-preview         карусель статей
└── widgets/page-footer          подвал
```

Страница отвечает только за состав и вертикальный ритм секций. Всё
оформление внутри секции принадлежит виджету, всё оформление карточки —
сущности.

## Тексты и данные

Разделены намеренно.

**Подписи интерфейса** живут в словарях `config/locales/ru.json` внутри своего
слайса. Пространство имён выводится из имени слайса: `page-header` →
`pageHeader`. Язык по умолчанию — русский, он подключается на сервере, любой
другой язык догружается отдельным чанком.

```
src/widgets/page-header/config/locales/ru.json  →  t("pageHeader.cta")
```

> При добавлении **нового** файла словаря нужен перезапуск dev-сервера:
> список словарей собирается через `import.meta.glob` на этапе загрузки модуля,
> и горячая перезагрузка новые файлы не подхватывает.

**Контент** (товары, подборки, статьи) лежит в
`src/pages/engagement-rings/api/mock/*.json` и отдаётся через асинхронные
функции в `api/index.ts`. Форма данных совпадает с тем, что вернул бы бэкенд,
поэтому при появлении настоящего API меняются только тела функций, компоненты
не трогаются.

Страница загружает каждую группу данных через `useAsyncData` со своим ключом и
показывает одно из трёх: заглушку на время загрузки, блок ошибки с повтором или
содержимое. Заглушки живут рядом со своими виджетами и повторяют их сетку,
чтобы высота секции не прыгала.

> Ожидание не отключено, поэтому сервер отдаёт страницу уже с данными и в
> обычной загрузке заглушки не мелькают. Их видно при повторной загрузке на
> клиенте и после ошибки. Когда часть данных станет пользовательской или
> медленной, достаточно отключить у такого запроса серверную загрузку, и та же
> заглушка начнёт показываться при каждом заходе.

Приведение типов встречается ровно в одном месте — на границе с моками:
импорт JSON расширяет строковые литералы до `string`, из-за чего теряется
объединение вариантов металла.

В коде запрещена кириллица (правило ESLint), поэтому строку невозможно
случайно зашить в компонент мимо словаря или мока.

## Дизайн-система

### Токены

Двухуровневые CSS-переменные в `src/shared/assets/styles/tokens/`:

- **примитивы** — сырые значения палитры и шкал;
- **семантика** — роли: `--color-text-secondary`, `--color-bg-surface-subtle`,
  `--color-action-primary-bg`.

Компоненты используют только семантику. Смена палитры — правка одного файла.

### Типографика

Десять стилей из макета собраны в группы `--text-*` и применяются миксином:

```scss
.product-card__title {
  @include text("body-m-light");
}
```

Миксин раскрывает семейство, размер, начертание, интерлиньяж, межбуквенное
расстояние и регистр. Отдельного компонента-обёртки для текста нет: разметка
остаётся семантической, а стиль задаётся классом БЭМ.

### Разделительные линии

Обводка в Figma не увеличивает высоту блока, а `border` в CSS — увеличивает.
Из-за этого каждая секция с рамкой становилась на пиксель выше макета. Для
таких линий есть миксин `hairline($side)`, который рисует их внутренней тенью:

```scss
.page-header__row {
  @include hairline(bottom);
}
```

### Сетка и адаптивность

Контейнер ограничен 1920 и имеет боковые поля, плавно растущие с 16 до 24
пикселей. На 1440 это даёт ровно те 1392 пикселя контента, что и в макете.

Секции построены на сетках с долевыми колонками, а не на фиксированных
пикселях, поэтому раскладка переживает изменение ширины окна.

Макетов планшета и мобильного заказчик не давал, поведение на этих ширинах
выбрано нами:

| секция          | планшет                            | мобильный                 |
| --------------- | ---------------------------------- | ------------------------- |
| шапка           | лишние пункты уходят в «Ещё»       | бургер и боковая панель   |
| герой           | фото сверху, текст под ним         | то же, фото 4:3           |
| плитки фильтров | лента с прокруткой                 | лента, две плитки в кадре |
| полка товаров   | две колонки, крупная во всю ширину | одна колонка              |
| подборки        | две колонки                        | две колонки               |
| консультация    | в столбик                          | в столбик                 |
| блог            | заголовок сверху, лента под ним    | карточка и край следующей |
| подвал          | две колонки                        | одна колонка              |

Пункты меню в шапке прячутся по одному. Ширины, на которых очередной пункт
перестаёт помещаться между логотипом и кнопками, посчитаны по отрисованным
подписям и лежат списком в `PrimaryNav.vue`. Решение принимает CSS, а не
замер в браузере: замерить можно только после гидратации, и строка меню
перестраивалась бы на глазах при каждом обновлении страницы. Обратная сторона
— список ширин привязан к текущим подписям: если пункты переименуют, значения
нужно пересчитать.

## Иконки и изображения

Иконки — отдельные SVG в `src/shared/assets/icons/`, подключаются через
`vite-svg-loader` как компоненты и наследуют цвет от родителя. Компонент
`Icon` находит нужный файл по имени:

```vue
<Icon name="search" :size="24" />
```

Логотип вынесен в отдельный компонент `Logo` с вариантами для шапки и подвала.

Изображения экспортированы из макета в `public/images/` и уменьшены до
удвоенного размера отображения. Фотографии в JPEG, кольца с прозрачным фоном в
PNG. Исходники весили 55 МБ, в репозитории 3.7 МБ.

Отдаёт их модуль `@nuxt/image`: формат и качество заданы один раз пресетом
`photo` в `nuxt.config.ts`, поэтому в браузер уходит webp. Ширины на каждом
брейкпоинте собирает помощник `imageSizes` из `src/shared/config/image.ts` —
модуль строит по одному варианту на перечисленный экран, и значение держится,
пока следующий брейкпоинт не объявит своё.

```vue
<NuxtImg :src="image" :sizes="imageSizes({ xs: 100, lg: 50 })" preset="photo" />
```

Картинка первого экрана грузится с предзагрузкой и высоким приоритетом,
остальные отложены. Апскейла не бывает: если запрошенная ширина больше
исходника, преобразователь отдаёт исходный размер. По странице это 818 КБ
вместо 3771 КБ исходных файлов.

## Анимация появления

Секции проявляются при попадании в область просмотра, элементы внутри — по
очереди: каждый следующий стартует на середине предыдущего.

Все настройки собраны в `src/shared/config/motion.ts`: одна длительность, шаг
как её половина и готовые наборы, которые секция подключает целиком.

```vue
<Motion v-bind="revealCascade" tag="section" class="size-guide-banner">
```

| набор                 | поведение                                              |
| --------------------- | ------------------------------------------------------ |
| `revealSection`       | блок появляется целиком                                |
| `revealCascade`       | дочерние элементы по очереди                           |
| `revealCascadeFading` | каскад без вертикального сдвига, для лент с прокруткой |

Секции идут строго по порядку: попав в кадр, каждая встаёт в общую очередь
`src/shared/lib/revealQueue.ts`, упорядоченную по положению в документе, поэтому
нижняя секция никогда не появится раньше верхней. Очередь передаёт ход на
середине предыдущей анимации — тем же перехлёстом, что и элементы внутри
каскада, — иначе первый экран собирался бы вдвое дольше. Секцию, которую
читатель уже пролистал, очередь показывает мгновенно, без анимации, чтобы не
догонять его.

Анимацией управляет компонент `Motion` поверх GSAP: библиотека грузится
отдельным чанком и только когда доходит до дела.

Чтобы контент не мелькал, элементы приходят с сервера уже скрытыми. Скрытие
включается классом, который проставляет крошечный скрипт в шапке документа до
первой отрисовки. Без JavaScript класс не появляется и контент виден сразу;
при системной настройке «уменьшить движение» анимация выключается.

Скрытие подстраховано с трёх сторон, иначе сбой оставил бы страницу пустой:
задача в очереди выполняется в `try/catch` и ограничена таймаутом, компонент
снимает скрывающий класс в `finally` даже когда библиотека не загрузилась, а в
самих стилях лежит отложенная анимация, которая возвращает непрозрачность,
если скрипты не отработали вовсе.

Картинка первого экрана анимируется не очередью, а средствами CSS: очередь
стартует только после загрузки библиотеки, а крупнейшая отрисовка страницы —
это именно она. Длительность берётся из токена `--duration-reveal`, с которым
сверяется и `motion.ts`.

## Принятые решения и допущения

Отмечаю то, чего в макете нет и что решено на нашей стороне:

- **Состояния наведения.** В макете у всех компонентов выставлено единственное
  состояние. Наведение сделано минимальным: подсветка прозрачностью для ссылок
  и иконок, потемнение основной кнопки, потемнение рамки у контурной.
- **Избранное.** Кольцо в избранном показывается залитым красным сердцем.
  Форма взята из контура иконки макета, цвет добавлен отдельным токеном, потому
  что в палитре бренда красного нет.
- **Панель фильтров.** Экрана с фильтрами в макете нет. Кнопка «Фильтры»
  раскрывает под собой аккордеон с заглушкой на месте будущих полей.
- **Форма связи.** Кнопки «Связаться с нами», «Связаться с экспертом» и
  «Записаться на просмотр» открывают модальное окно с заглушкой: макета формы
  заказчик не давал. Окно построено на элементе `dialog`, поэтому фокус,
  инертность остальной страницы и закрытие по Escape достаются от браузера.
- **Кнопки листания карусели.** В макете под них зарезервировано место, но сам
  элемент скрыт, внешний вид неизвестен. Карусель листается колесом, пальцем и
  клавиатурой, стрелки не рисовал.
- **Иконка сайта.** В макете её нет, поставлена временная монограмма.
- **Четвёртая карточка блога** воспроизводит заглушку из макета.

## Доступность

- Первым в порядке табуляции идёт скрытая ссылка «Перейти к содержимому»: она
  переносит фокус за шапку, чтобы не проходить её целиком на каждой странице.
- Обвод фокуса один на весь проект, описан в `base/_globals.scss`. У карточек
  со ссылкой во всю площадь он рисуется вокруг карточки, а каруселям добавлен
  внутренний отступ, иначе прокручиваемая область срезала бы обвод.
- Все интерактивные элементы — настоящие ссылки и кнопки, доступны с клавиатуры.
- У иконок без подписи обязательный текстовый ярлык, у кнопки избранного
  меняется и ярлык, и состояние нажатия.
- Декоративные изображения скрыты от скринридеров, свотчи металлов имеют
  скрытые подписи.
- Карточки товара и статьи кликаются целиком, но доступное имя ссылки остаётся
  на заголовке.

## Производительность

Замеры Lighthouse на production-сборке, мобильный профиль:

| правка                            | оценка |
| --------------------------------- | ------ |
| исходное состояние                | 74     |
| сжатие ответов сервера            | 81     |
| HTTP-клиент вне стартового бандла | 85–95  |

Что сделано: отрисованная страница отдаётся сжатой (199 КБ → 18 КБ), axios
подгружается при первом запросе, картинки идут в webp по размеру места, у
первого экрана предзагрузка. Сдвигов вёрстки нет, время блокировки 30–60 мс.

Разброс последней строки — фоновая нагрузка машины, на которой шли замеры.
Как мерить правильно, описано в разделе [про сборку](#проверять-работу-нужно-на-сборке).

Что осталось узким местом:

- **Шрифты, 192 КБ на три начертания** — самая тяжёлая позиция страницы.
  Подрезка до кириллицы и латиницы дала бы примерно минус две трети, но это
  изменение лицензионных файлов, нужно сверяться с лицензией.
- **Два небольших файла стилей** блокируют первую отрисовку: Nuxt выносит их
  ссылками, потому что компоненты общие для макета и страницы.
- **Стартовый бандл 87 КБ**, около трети не используется. Предкомпиляция
  словарей сняла бы ещё порядка 15 КБ.

## Тесты

Vitest с окружением Nuxt, файлы лежат рядом с проверяемым кодом
(`*.spec.ts` в том же сегменте). Запуск — `npm run test`, в режиме наблюдения
`npm run test:watch`; в CI это отдельная задача.

Покрыта логика, которая ломается молча:

| что                          | почему это важно                                                          |
| ---------------------------- | ------------------------------------------------------------------------- |
| очередь появления секций     | упавшая или зависшая анимация не должна оставлять страницу пустой         |
| счётчик блокировок прокрутки | окно поверх мобильного меню не должно разблокировать страницу             |
| ширины картинок              | пропуск брейкпоинта означает пережатую или размытую картинку              |
| формат цены                  | единственное место с денежным форматированием                             |
| данные страницы              | моки импортируются как JSON, и объединение вариантов металла там теряется |

И поведение, которое легко сломать правкой разметки: модальное окно
(открытие, три способа закрытия, блокировка прокрутки), аккордеон фильтров,
кнопка избранного и выпадающее меню шапки.

Сворачивание пунктов меню тестами не покрыто: оно живёт в CSS и зависит от
ширины отрисованного текста, которой в тестовом DOM нет. Вместо теста в режиме
разработки работает предупреждение — если строка меню перестала помещаться, в
консоли появится сообщение с числами.

## Качество кода

Проверки запускаются локально и в CI, а также на pre-commit через Husky:

| команда              | что делает                                           |
| -------------------- | ---------------------------------------------------- |
| `npm run test`       | Vitest: логика и ключевые компоненты                 |
| `npm run lint:check` | ESLint (Vue, доступность, импорты) и Stylelint (БЭМ) |
| `npm run typecheck`  | проверка типов через `vue-tsc`                       |
| `npm run format`     | Prettier                                             |
| `npm run build`      | линт, типы и production-сборка                       |

Сообщения коммитов проверяются Commitlint по Conventional Commits.

Подробности конфигурации — в [SETUP.md](./SETUP.md).
